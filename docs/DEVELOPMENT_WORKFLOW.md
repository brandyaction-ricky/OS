# Brandy OS 개발 운영 규칙

## 정본 역할

- GitHub `main`: 배포 가능한 코드의 유일한 정본
- Brandy OS `개발 관리`: 프로젝트 상태, 작업·검증·배포 이력의 정본
- ChatGPT Work: 맥락 조회, 코드 수정, 검증, 기록을 수행하는 실행 환경
- 개인 옵시디언: 아이디어와 참고 자료 보관소이며 현재 코드 상태의 정본으로 사용하지 않음

## 한 작업의 표준 흐름

1. GitHub `main`을 최신으로 확인한다.
2. OS의 `get_project_context`로 현재 프로젝트 상태와 최근 이력을 읽는다.
3. `work/<주제>-<날짜>` 브랜치에서 한 가지 목적의 변경만 진행한다.
4. 린트, 타입 검사, 테스트, 프로덕션 빌드를 통과시킨다.
5. `create_development_log`에 브랜치, 커밋, 변경 파일, 검증 결과, 위험과 다음 단계를 기록한다.
6. DEV 배포 후 `record_deployment`로 URL과 확인 결과를 기록하고 사용자의 검수를 받는다.
7. 사용자가 정확히 `운영 반영 승인`이라고 승인한 뒤에만 운영 배포한다.
8. 운영 배포와 사후 확인 결과를 다시 `record_deployment`에 기록한다.

## 브랜치와 커밋

- 작업 브랜치: `work/<기능>-YYYYMMDD`
- 긴급 수정: `hotfix/<문제>-YYYYMMDD`
- 커밋은 되돌릴 수 있는 한 가지 논리 변경으로 제한한다.
- 생성물, 비밀키, `.env*`, 로컬 임시 파일은 커밋하지 않는다.

## 개발 로그 필수 항목

- 무엇을 왜 바꿨는지
- 저장소, 브랜치, 커밋 SHA
- 주요 변경 파일
- 실행한 검증과 결과
- DEV 또는 운영 환경과 결과 URL
- 남은 위험, 알려진 문제, 다음 단계

## 배포 안전장치

- DEV 확인 전 운영 배포 금지
- 데이터베이스 마이그레이션은 하위 호환·추가형을 우선하고 되돌리기 방법을 기록
- 운영 배포에는 승인 근거가 필요하며, MCP의 `record_deployment`도 이를 검사
- 실패 시 새 변경을 덧대기 전에 마지막 정상 배포로 롤백할 수 있는지 먼저 확인
