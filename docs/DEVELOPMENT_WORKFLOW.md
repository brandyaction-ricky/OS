# 혼자 Work로 개발하고 OS에 기록하기

직원은 OS에 수정 요청을 남기고, 대표는 요청을 Work에 전달해 개발한다. 코드는 GitHub에서 버전 관리하고 처리 결과는 원래 OS 요청에 연결한다.

## 어디에 무엇을 남기나

| 위치 | 관리할 내용 |
| --- | --- |
| OS `/knowledge/development` | 직원 수정 요청, 처리 상태, 해결 내용, 개발·배포 이력 |
| GitHub 작업 브랜치·PR | 실제 코드 변경, 커밋, 코드 검토와 자동 검사 결과 |
| GitHub `main` | 병합된 코드. 운영에 배포됐는지는 배포 서비스에서 별도로 확인 |
| Vercel 배포 | 환경, 배포 상태, URL, 실제 배포 커밋 SHA |
| `CURRENT_STATE.md` | 다음 채팅이 읽을 짧은 인수인계. 상세 작업 기록은 OS에 연결 |
| ChatGPT Work | 요청 확인, 개발, 검증, GitHub 변경, OS 결과 기록 |

OS 요청이나 배포 기록을 저장하는 것만으로 Work가 실행되거나 코드가 배포되지는 않는다. 요청을 등록하면 개발 관리에서 확인할 수 있으며, 개발 시작은 대표가 Work에 전달한다. 상시 자동 감시·자율 개발 연결은 별도 설정이 필요하다.

## 직원: 불편한 화면에서 요청하기

1. 화면 상단의 수정 요청 진입점을 열고 문제가 있는 페이지를 확인한다.
2. 문제 제목, 재현 순서, 기대한 결과와 실제 결과를 적는다. 개선 아이디어는 원하는 사용 흐름을 적는다.
3. 접수된 요청을 개발 관리에서 확인한다. 비밀번호, API 키, 고객 개인정보는 본문에 넣지 않는다.
4. 처리 결과를 확인하고 같은 문제가 남아 있으면 요청을 다시 접수한다.

요청 하나에는 문제 하나를 담는다. 예: “검색어 입력 → 상태 필터 선택 → 결과가 사라짐. 검색어와 상태를 함께 적용한 결과가 보여야 함.”

## 대표: 요청 하나를 끝내는 순서

1. **확인:** 개발 관리에서 미해결 요청을 보고 처리할 요청을 연다.
2. **전달:** 해당 요청의 Work용 요청문을 복사해 Work에 붙여 넣는다. 이전 채팅을 그대로 기억한다고 가정하지 않는다.
3. **개발:** 원격 저장소와 OS 요청의 최신 상태를 확인하고, 별도 브랜치·작업 디렉터리에서 수정한다. 해당 요청을 `수정 중`으로 관리한다.
4. **검증:** 변경 범위에 맞는 테스트와 린트·타입 검사·빌드를 실행한다. Preview에서 실제 화면과 연결된 기능을 확인하고 `검수 요청`으로 넘긴다.
5. **반영:** 승인된 범위에 맞게 병합·배포하고, 운영 배포 SHA와 실제 동작을 확인한다. 요청에 해결 내용, 브랜치, 커밋, PR, 배포 URL을 남긴다.
6. **종료:** 해당 문제가 해결됐음을 확인한 후 `해결`로 바꾼다. 운영에 아직 반영하지 않았다면 배포 대기 사실을 남기고 완료로 과장하지 않는다.

| 상태 | 뜻 |
| --- | --- |
| 접수 (`backlog`) | 아직 처리하지 않았거나 재접수한 요청 |
| 수정 중 (`active`) | 원인 분석·개발 진행 중 |
| 검수 요청 (`review`) | 구현 결과를 확인 중. 운영 배포 완료를 뜻하지 않음 |
| 해결 (`done`) | 요청한 문제가 실제 대상 환경에서 해결됨 |
| 보류 (`blocked`) | 외부 연결, 정보, 의사결정 등 필요한 조건을 기다림 |

직원은 `검수 요청` 또는 `해결` 상태에서도 문제가 남아 있으면 다시 접수할 수 있다. 관리자용 상태·해결 결과 변경은 직원의 요청 접수와 구분한다.

## 페이지별 채팅과 버전 관리

- 동일한 파일을 동시에 바꾸지 않도록 채팅마다 별도 작업 디렉터리와 브랜치를 사용한다. 권장 이름은 `codex/<요청-주제>-YYYYMMDD`다.
- 새 작업은 원격 `main`과 미병합 PR을 함께 확인한다. 필요한 선행 변경이 PR에만 있으면 그 의존성과 기준 커밋을 기록한다.
- 요청 ID를 커밋·PR·개발 로그에 연결한다. 변경 목적이 다른 작업은 별도 PR로 나눈다.
- 공통 레이아웃, 인증, DB 구조를 바꾸는 작업은 통합 담당 채팅에서 다른 브랜치와 조율한다.
- 병합 직전에 원격 변경과 충돌을 확인하고, 통합 결과에 필요한 검증을 실행한다. 다른 채팅의 변경을 덮어쓰지 않는다.

## 승인과 운영 데이터

사용자가 이미 “이 변경을 배포해줘”처럼 대상과 범위를 명시했다면 그 승인을 이어서 사용한다. 특정 문구를 다시 요구하지 않는다. 조사·수정·검증·검토 가능한 결과 준비는 요청 범위 안에서 진행한다.

운영 반영이 아직 승인되지 않았다면 수정 내용, 검증 결과, 영향 범위가 확인 가능한 상태까지 준비한 뒤 승인받는다. 승인된 범위를 넘는 데이터 삭제, 권한 변경, 추가 비용 등은 별도로 설명한다. 승인 근거는 시점과 해당 요청 범위로 기록하며 비밀값은 포함하지 않는다.

- 기존 운영 데이터와 계정을 보존하고, DB 변경은 추가형·하위 호환 방식을 우선한다.
- Preview라는 이름만으로 DB가 운영과 분리됐다고 가정하지 않는다. 쓰기 검증 전 실제 연결 대상을 확인한다.
- Secret은 보안 저장소에서 관리하고 소스·로그·요청문·PR에 넣지 않는다.
- 운영 배포 기록의 `approval_reference`에는 이미 제공된 승인 근거를 사용할 수 있다. 기록 자체는 배포 실행이나 승인 발급 기능이 아니다.

## 개발·배포 기록

개발 관리에서 개발 로그와 배포 결과를 각각 기록한다. Work에 OS 원격 MCP가 연결되어 있으면 `get_project_context`, `create_development_log`, `record_deployment`를 사용할 수 있다. 연결이 없으면 OS 화면에서 같은 내용을 기록한다. 연결 방식은 [MCP 안내](../integrations/mcp/README.md)를 참고한다.

개발 로그에는 요청 ID, 변경 이유, 저장소·브랜치·커밋, 주요 변경 파일, 실행한 검증과 결과, 남은 일과 다음 행동을 적는다. 배포 기록에는 환경, 실제 배포 SHA, 배포 URL, 상태, 사후 검증 결과와 필요한 승인 근거를 적는다.

`빌드 통과`, `Preview 검수 완료`, `main 병합`, `운영 배포 Ready`, `운영 기능 검증 완료`를 각각 구분한다. Vercel이 Ready여도 요청한 기능의 동작 확인이 끝났다는 뜻은 아니다. 확인하지 못한 항목은 이유와 함께 남긴다.

이 저장소의 공개 여부와 열람자를 고려해 GitHub에는 기술적 변경과 비식별 요청 ID만 기록한다. 직원 연락처, 고객 자료, 내부 원문은 OS의 접근 통제된 요청에 남긴다.

## 다음 Work 채팅 시작문

요청 상세의 Work용 요청문을 우선 사용한다. 전체 작업을 이어갈 때는 아래처럼 시작한다.

```text
brandyaction-ricky/OS 개발을 이어가자.

CURRENT_STATE.md, docs/DEVELOPMENT_WORKFLOW.md, 원격 main과 미병합 PR,
OS /knowledge/development의 해당 요청과 최신 개발 로그를 확인해줘.
main의 커밋과 실제 운영 배포 커밋을 별도로 대조해줘.

이번 대상: [OS 요청 ID 또는 담당 페이지]
완료 기준: [사용자가 할 수 있어야 하는 행동]
실행 범위: [조사 / 개발 및 Preview 검수 / 운영 배포까지]

별도 작업 브랜치에서 기존 데이터와 다른 작업을 보존하며 진행해줘.
이미 승인된 범위는 반복 확인하지 말고, 범위를 넘는 변경만 알려줘.
결과에는 실제 검증한 내용과 확인하지 못한 내용을 구분하고,
OS 원본 요청에 해결 내용·브랜치·커밋·PR·배포 결과를 연결해줘.
```
