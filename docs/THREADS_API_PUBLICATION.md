# 개인 Threads 원고 — 공식 API 발행 연결

## 범위와 상태

Aside는 자료 조사·원고 작성·미승인 결과 저장까지 맡는다. 원고 채택, 최종 검수,
게시 계정 선택과 실제 발행은 사람이 OS에서 수행한다. Aside로 Threads 웹사이트의
게시·답글 버튼을 누르거나 토큰을 받아 직접 API를 호출하지 않는다.

이번 연결은 **최종 검수된 텍스트 원고 1~30개를 한 글타래로 발행**하는 범위다.
본문 뒤의 관점 댓글·적용 대댓글·출처는 저장된 순서대로 바로 앞 글의 답글이 된다.
연속 글을 합쳐 쓰거나 문단을 다시 작성하지 않는다. 각 글은 공백·줄바꿈 포함 500자 이하.
이미지·영상 첨부, 예약 시각의 자동 발행, 댓글 답변 자동화는 이 변경의 범위가 아니다.
기존 일정은 발행 알림이며, 예약만으로 API가 게시하지 않는다.

현재 운영 화면을 2026-10-29 읽기 전용으로 확인한 결과 Meta는 연습용 모드이고
확인한 계정에는 Threads 연결이 없었다. 새 코드가 존재하는 것과 실계정 연결 완료는 다르다.
이번 개발 중에는 실제 Threads 게시·답글, 운영 설정 변경, 원격 DB 마이그레이션을 하지 않는다.

## 직원이 사용하는 순서

1. 기존 수집 → 주제 선택 → 집필을 진행하고 미승인 결과를 확인한다.
2. 첫 실행의 종료점은 **미승인 초안 저장**이다. 이 단계에서 발행 화면으로 진행하지 않는다.
3. 별도 발행 단계에서 사람이 원고를 채택하고 ‘최종 확인’의 직접 확인을 마친다.
4. ‘발행’에서 승인한 쓰레드를 선택하고 사용할 Threads 계정을 확인한다.
5. 글타래 전체와 연결 계정을 확인한 뒤 확인란을 체크하고 공식 API 발행 버튼을 누른다.
6. OS의 완료 상태와 원문 링크를 확인한다. 일부만 게시됐다면 완료 개수를 먼저 읽는다.
   재시도 가능한 경우에만 미게시 부분을 이어서 올린다. 결과 확인이 필요하다고 표시되면
   다시 게시하거나 브라우저로 대신 올리지 않고 담당자에게 해당 OS 링크를 전달한다.

## 서버 경계

- 로그인한 원고 소유자만 발행을 요청한다. 원고의 검수자는 기존 최종 확인 권한을 따른다.
- 게시 계정은 본인 연결 또는 팀 공유된 실제 Threads 연결로 제한한다. 관리자라는 이유만으로
  다른 사람의 비공유 계정을 사용할 수 없다. 재시도에도 계정·토큰·공유 상태를 다시 확인한다.
- 사람의 요청은 원고 버전과 계정을 포함하며, 원고 본문은 서버가 승인된 기록에서 읽는다.
  클라이언트가 보낸 문안·게시 완료 ID·승인 표시를 신뢰하지 않는다.
- 전용 서버 저장소에서 발행 상태와 게시 ID를 보관한다. 일반 원고 수정 API로 이를 만들거나
  바꿀 수 없다. 동시 요청, 부분 발행 중 원고 변경, 결과 불명확 후 자동 재게시를 차단한다.
- 실발행 성공과 기존 발행 이력 반영은 구분 없이 완료되어야 한다. 연습용 결과를 실게시 이력으로
  기록하지 않는다. 토큰은 기존 암호화 저장소를 재사용하며 브라우저·Aside·로그에 전달하지 않는다.
- 전용 기능 스위치 `THREADS_AUTOMATION_PUBLISH_ENABLED`는 기본 false이다.
  실제 발행에는 `META_MODE=live`와 기존 `META_LIVE_PUBLISH_ENABLED=true`도 필요하다.
  기존 다른 콘텐츠 발행 경로의 승인 체크포인트·환경 조건을 완화하지 않는다.

## 연결 및 배포 전에 마칠 일

1. 신규 발행 저장소/RPC/원고 보호 트리거를 포함한 고정 버전을 검수하고 DEV 적용을 승인받는다.
   모의 외부 응답으로 저장·권한·중복·부분 실패를 확인한다. 이번 시점의 로컬 모의 검수와
   실제 DEV DB 검수 결과는 따로 기록한다.
2. 회사 Meta 앱에 Threads 사용 사례가 있는지 확인하고 해당 계정의 앱 역할/초대 수락을 확인한다.
   앱 역할 밖 사용자를 연결하는 경우 필요한 Meta 심사·접근 권한 상태를 확인한다.
3. 기존 서버 설정 `META_THREADS_APP_ID`, `META_THREADS_APP_SECRET`, `META_TOKEN_ENCRYPTION_KEY`,
   `OS_PUBLIC_URL`을 지정 환경에서 준비한다. 비밀값을 채팅·직원 요청문·파일에 적지 않는다.
   OAuth 콜백은 `{OS_PUBLIC_URL}/api/v1/meta/callback`이다.
4. 계정 소유자가 OS ‘내 계정 → Threads’의 Meta 인증을 직접 완료한다. 현재 구현이 요청하는
   권한을 Meta 화면에서 확인한다. 직원과 같이 쓸 경우 소유자가 OS에서 팀 공유 여부를 정한다.
5. 실계정 연결·읽기 확인과 운영 배포는 별도 승인 범위다. 실제 게시 시험은 이번 요청에서
   금지되어 있으므로 하지 않는다. 활성화 전 미검증인 실발행 성공·한도·권한을 완료로 보고하지 않는다.

## 공식 자료

- [Meta 공식 Threads API 컬렉션](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api)
  — OAuth, 텍스트 컨테이너, 발행, `reply_to_id`를 통한 답글.
- [Meta 공식 게시 한도 조회](https://www.postman.com/meta/threads/request/34203612-f4590341-9bee-44f5-901b-606078a03c96)
  — 고정 숫자를 운영 보장으로 쓰지 않고 계정별 응답과 플랫폼 거절을 확인한다.

공식 API 사용 자체가 계정 제재를 막아준다고 보장하지 않는다. 게시 내용과 플랫폼 이용 기준은
계속 적용된다. 이번 변경의 목적은 공식 연결·명시적 사람 확인·결과 기록을 갖춘 발행이다.
