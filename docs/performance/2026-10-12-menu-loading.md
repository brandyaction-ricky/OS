# 메뉴 조회 구조·성능 점검 — 2026-10-12

## 범위와 근거

- 저장소의 메뉴 정의, 화면 Provider, API, 서버 조회 함수 및 마이그레이션을 연결해 점검했다.
- 아래 메뉴별 연결은 **로컬 코드와 스키마의 정적 분석**이다. 정적 분석으로 응답 시간을 측정하거나 특정 SQL을 실제 병목으로 확정하지 않는다.
- 로컬 마이그레이션은 47개이며 테이블 생성 선언은 95종이다. 별도의 운영 메타데이터 읽기에서도 **테이블 95개, RLS 활성화 95개**를 확인했다.
- 운영 데이터의 내용, 직원 정보, 문서 식별자는 이 문서에 기록하지 않는다. 이 작업에서 운영 DB·스키마·정책을 변경하지 않았다.
- 실제 체감 시간은 브라우저 인증, API 왕복, DB 조회, 응답 크기, 화면 렌더링의 합이다. 개선 이후 수치는 배포 환경에서 별도 측정해야 한다.

## 운영 관찰값과 해석 한계

- 개선 전 운영 회사 정본에서 새로고침 후 전체 정본 842개가 표시될 때까지 **10,791ms**를 관찰했다. 단일 표본이며 브라우저 조작 도구의 오버헤드가 포함된다. 순수 API 응답 시간이나 반복 측정의 평균으로 해석하지 않는다.
- 운영 `pg_stat_statements`의 문서 관련 관찰 항목은 누적 **87,879회**, 평균 **80.63ms**, 최대 **11,390.8ms**였다. 재무 관련 관찰 항목은 누적 **1,341회**, 평균 **166.47ms**, 최대 **7,339.5ms**였다.
- 위 SQL 통계의 누적 기간은 확인하지 못했다. 현재 페이지의 요청 수, 오늘 발생한 횟수, 전체 API 처리 시간 또는 이번 배포 전후 비교가 아니다. 드물게 긴 DB 실행이 있었다는 단서로만 사용한다.
- 문서 842개·활성 구성원 10명을 가정한 **정적 최소 모델**에서는 정본 초기 로딩의 DB 읽기 요청을 **40회 → 6회**로 줄이는 것으로 추산했다. 이는 코드 경로 계산이며 운영 추적 실측이 아니다. 상위 문서, 회의 연결, 제안 수, 담당자 수와 페이지 수에 따라 실제 횟수는 달라진다.

## 이번 수정의 조회 동작

- 사용자 API 인증: 검증된 사용자 확인 후 서로 독립적인 프로필·HR 상태 조회를 병렬 수행한다. 인증·비활성 계정·퇴사·비밀번호 변경 검사는 유지한다.
- 회사 정본: `/knowledge/canon`이 정본 목록 필드·관련 제안 유무·담당자 이름만 반환한다. 문서는 ID 커서로 페이지를 넘겨 OFFSET에서 건너뛰는 행의 계층 권한 재평가를 줄인다. 목록을 열 때 노트·임시저장·템플릿·회의·감사 자료를 함께 받지 않는다. 편집이나 새 문서 기능에서 필요해지면 전체 workspace를 로드한다.
- 회의록 목록: `/knowledge/meetings`의 전용 목록 조회를 사용한다. 목록 진입 시 전체 문서 workspace를 준비하지 않고, 상세·생성·공통 바로가기 기능에 필요한 시점에 준비한다.
- 문서 권한 조회: 서버 조회에 필요한 정책 필드가 이미 있으면 같은 문서를 다시 가져오지 않는다. 필드가 부족한 경우 정책 필드만 좁혀 가져오고 최대 4묶음을 병렬 조회한다. 상위 문서와 회의의 읽기 제한·누락 시 접근 거절은 유지한다.
- 공통 기록·구성원 읽기: 동일 토큰과 URL의 진행 중 요청만 합친다. 완료 응답을 영구 캐시하지 않고, 저장 전후에는 기존 읽기를 재사용하지 않는다.
- 기록 전체 조회: 첫 페이지는 정확한 count를 유지해 화면 목록과 요청을 공유한다. 두 번째 페이지부터 `count=none`을 사용한다. 첫 count와 페이지 길이로 종료하며, API 기본 응답의 정확한 total 계약은 유지한다.
- 팀 화면: 탭·선택·담당자 필터는 이미 받은 자료를 재사용한다. 일정의 주·월/날짜 범위가 달라지거나 저장을 마친 경우에 재조회한다. 부재 조회는 다른 일정 조회와 함께 시작한다.
- 재무: `/finance/workspace?batch=1`에서 한 번 인증하고 최대 4개 DB 조회를 동시에 진행한다. 자료 하나라도 실패하면 부분 장부를 성공 응답으로 제공하지 않는다. 응답이 3.5MB를 넘으면 명시적 신호를 반환하고 기존 resource/offset 방식으로 나눠 읽는다. 다른 오류·권한 실패는 이 fallback 대상이 아니다.
- HR 사이드바 배지: 전체 workspace 10종 대신 계산에 필요한 프로필·직원·연차 크레딧·휴가 신청·촉진·서류의 6종을 읽는다. 별도 테이블 SELECT는 계산용 필드로 좁히고 기존 직원 RPC를 유지한다. 배지를 위해 계약·양식·공휴일·설정을 읽지 않는다. 각 자료가 페이지 한도보다 많으면 해당 자료의 추가 페이지 조회는 남는다.
- 설정: 작동 상태에서는 health와 연결 상태, 권한에서는 구성원, 회사 설정에서는 구성원과 브랜드 등 해당 화면에 필요한 조회만 수행한다. 세션 준비 전에 불완전한 인증으로 요청하지 않으며 이전 화면 응답이 새 화면을 덮어쓰지 않는다.
- 전역 알림: 패널이 닫혀 있을 때 수정 요청 목록·상태별 summary를 조회하지 않는다. 읽지 않은 알림 개수 조회는 유지하며 패널을 열면 요청 상세 요약을 읽는다.
- health: 서로 독립적인 문서 DB 확인과 조직 DB 확인을 병렬 수행한다.

## 스키마와 추가 검토 지점

주요 테이블군은 문서 10종, knowledge 관련 3종, HR 10종, 재무 21종, AI 실행 3종, 콘텐츠 승인/검수 2종 및 이전 ERP 10종이다. 나머지는 프로필·연결·감사·검색 등 공통 기능이다. 범주별 숫자는 접두사 분류이며 모든 범주를 더한 합으로 전체 테이블 수를 계산하지 않는다.

- HR read 정책은 이미 `(select os_has_hr_access())` 등 공통 권한 결과를 재사용하도록 구성돼 있다. 같은 최적화를 다시 적용할 필요는 없다.
- 문서 RLS는 행마다 상위 문서 경로와 프로필을 반복 확인할 수 있다. 정책 함수의 반복 비용을 줄이는 변경은 후속 검토 후보이며 이번 수정에서 RLS나 해당 DB 함수를 변경하지 않았다. 조상 문서 접근 제한을 생략하는 방식으로 해결하지 않는다.
- 일반 기록 목록은 `record_type` 필터와 `updated_at, id` 정렬을 쓴다. 기존 `(record_type, status, updated_at)` 인덱스는 status를 지정하지 않은 목록 정렬과 정확히 일치하지 않는다.
- 개인 자동화 인덱스는 owner/type/생성 시각을 포함하지만 목록은 수정 시각순이다.
- 위 인덱스 차이는 개선 **후보**다. 실행계획·행수·인덱스 크기를 확인하지 않고 운영 인덱스를 추가하지 않는다.
- 재무 전체 장부는 화면 계산과 변경 비교의 기준이다. 기간을 무조건 잘라 반환하면 잔액·관계 검증 결과가 달라질 수 있으므로 이번 작업은 전송 및 인증 반복을 줄이고 자료 범위를 유지한다.
- 내용 전체를 보관하는 서버 공용 캐시로 권한 비용을 숨기지 않는다. 계정별 격리와 권한 변경 반영이 먼저다.

## 확인 범위

Preview 실제 계정 확인에서 부재 조회가 기존 DB 권한 경계와 충돌하는 것을 발견했다. 개발·운영 양쪽에서 읽기 전용 `has_table_privilege`/`has_column_privilege`로 `service_role`의 휴가 요청 SELECT, 직원 `profile_id`·`display_name` SELECT가 모두 false임을 확인했다. 현재 부재 API는 그 역할로 직접 읽기 때문에 실패한다. 이번 변경은 부재 실패가 독립적인 회의·업무·팀원 표시까지 막지 않게 분리하고, 부재 미확인 경고를 유지한다. 최소 공개 필드만 반환하는 전용 RPC 등 DB 권한 문제의 근본 수정은 별도 승인·검증 대상이며 이번에는 권한을 확대하지 않는다.

개발 DB Preview에서 정본 851개의 목록 표시를 새로고침부터 2,215ms로 측정했다. 브라우저 조작 overhead를 포함한 단일 표본이며 운영 기준(정본 842개, 10,791ms)과 데이터·환경이 다르므로 운영 개선율로 환산하지 않는다.

신규 자동 검증은 정본·회의록 목록과 권한 경계, 팀 화면 전환 시 요청 횟수, 부재 병렬 시작, 재무 단일 인증·동시조회 제한·페이지 연속성·실패 및 큰 응답 fallback, 기록 count 생략 시 권한·필터·종료 조건, HR 배지 계산의 좁은 조회, 설정·알림의 조건부 조회를 다룬다. 관련 기존 테스트도 실행한다. 실제 통과 수와 수행하지 않은 검증은 최종 완료 기록에 남긴다.

운영 개인정보를 수정하는 테스트, 운영 schema migration, 부하 생성은 수행하지 않는다. 운영 배포 여부와 실제 메뉴 응답 시간은 최종 완료 기록에서 구분해 보고한다. 네트워크·서버 기동 비용까지 완전히 0으로 만들 수 있다는 보장은 하지 않는다.
